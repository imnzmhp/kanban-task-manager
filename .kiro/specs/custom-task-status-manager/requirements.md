# Requirements Document

## Introduction

この文書では、既存のkanban-task-managerプロジェクトを拡張する「カスタムタスク状態管理システム」の要件を定義します。このシステムにより、ユーザーはカスタムタスク状態の作成、修正、削除、並び替えが可能となり、データ整合性を保ちながら直感的なユーザー体験を提供します。この機能は既存のReact/TypeScriptコードベースと統合し、自動データ移行機能を備えたローカルストレージによる永続化を利用します。

## Glossary

- **カスタム状態**: ユーザーが定義可能なタスク状態（作成・修正・削除が可能）
- **状態管理システム**: カスタム状態を管理するシステムコンポーネント
- **状態設定モーダル**: カスタム状態を設定するためのUIコンポーネント
- **状態列**: かんばんボードにおいて状態を表現する視覚的な列
- **LAB色空間**: アクセシビリティ準拠の色生成のための知覚的に均一な色空間
- **表示順序**: 状態列の視覚的順序を決定する数値位置
- **移行システム**: レガシーデータを新フォーマットに変換するコンポーネント
- **タスク状態ストア**: 状態設定のローカルストレージ永続化レイヤー
- **ドラッグドロップ管理システム**: ドラッグ&ドロップによる状態並び替えを処理するコンポーネント
- **カラーパレット**: 状態の視覚化のための事前定義されたWCAG AA準拠色セット

## Requirements

### 要件1: 状態設定管理

**ユーザーストーリー:** かんばんユーザーとして、カスタムタスク状態を作成・管理したい。これにより、自分の特定のワークフロー要件にボードを適応させることができる。

#### 受入れ基準

1. 状態管理システムは、id、name、displayOrder、createdAtフィールドを含むカスタム状態をローカルストレージに保存する
2. ユーザーが新しい状態を作成するとき、状態管理システムは一意識別子を生成し、次の表示順序を割り当てる
3. ユーザーが状態名を修正するとき、状態管理システムは名前の長さが50文字を超えないことを検証する
4. 状態管理システムは常に最低1つの状態を維持する
5. ユーザーが最後に残った状態を削除しようとした場合、状態管理システムは削除を防止し、エラーメッセージを表示する

### 要件2: データ整合性を保った状態削除

**ユーザーストーリー:** かんばんユーザーとして、未使用の状態を安全に削除したい。これにより、既存のタスクを失うことなくボードを整理できる。

#### 受入れ基準

1. ユーザーが状態を削除しようとするとき、状態管理システムはその状態を持つタスクが存在するかチェックする
2. 対象状態を持つタスクが存在する場合、状態管理システムは削除を防止し、警告メッセージを表示する
3. 状態に関連するタスクがない場合、状態管理システムは削除を許可する
4. 状態が削除されるとき、状態管理システムは残りの状態の表示順序を更新する
5. 状態管理システムは監査目的で削除操作をログに記録する

### 要件3: ドラッグ&ドロップによる視覚的順序管理

**ユーザーストーリー:** かんばんユーザーとして、状態列をドラッグして並び替えたい。これにより、ワークフローを視覚的に整理できる。

#### 受入れ基準

1. 状態設定モーダルは、状態を現在の表示順序で表示する
2. ユーザーが状態を新しい位置にドラッグするとき、ドラッグドロップ管理システムは影響を受けるすべての状態の表示順序を更新する
3. 並び替えが完了するとき、状態管理システムは新しい順序をローカルストレージに保存する
4. 状態管理システムは、かんばんボード内のすべての状態列を新しい順序を反映するよう更新する
5. 順序変更が発生するとき、カラーパレットは新しい位置に基づいて色を再割り当てする

### 要件4: 位置ベースの色管理

**ユーザーストーリー:** かんばんユーザーとして、状態列が論理的な進行を作り出す視覚的に区別できる色を持つことを望む。これにより、ワークフローステージ間を簡単に区別できる。

#### 受入れ基準

1. カラーパレットは知覚的均一性のためにLAB色空間を使用して色を生成する
2. カラーパレットはすべての色がWCAG AAのコントラスト比4.5:1以上を満たすことを保証する
3. 状態位置が変更されるとき、カラーパレットは表示順序に基づいて自動的に色を再割り当てする
4. カラーパレットは、ワークフローステージを表現する左から右への色の進行を作成する
5. 状態設定モーダルが開くとき、カラーパレットは各状態の色プレビューを表示する

### 要件5: レスポンシブな状態名表示

**ユーザーストーリー:** かんばんユーザーとして、異なる画面サイズで状態名を明確に見たい。これにより、デスクトップとモバイルデバイスでボードを効果的に使用できる。

#### 受入れ基準

1. デスクトップ画面では、状態列は20文字より長い状態名を省略する
2. モバイル画面では、状態列は15文字より長い状態名を省略する
3. 状態名が省略されるとき、状態列は省略記号を表示し、完全な名前のツールチップを提供する
4. 状態列は320px～380pxの固定列幅を維持する
5. 画面サイズが変更されるとき、状態列はそれに応じて省略制限を調整する

### 要件6: 設定インターフェース統合

**ユーザーストーリー:** かんばんユーザーとして、直感的なインターフェースを通じて状態管理にアクセスしたい。これにより、ワークフローを中断することなくボードを設定できる。

#### 受入れ基準

1. かんばんボードは、ボードヘッダーにギアアイコンの設定ボタンを表示する
2. 設定ボタンがクリックされるとき、状態設定モーダルが開く
3. 状態設定モーダルは、現在の状態をその名前、色、順序とともに表示する
4. 状態設定モーダルは、状態の追加、編集、削除、並び替えのコントロールを提供する
5. 変更が保存されるとき、状態設定モーダルは閉じて、かんばんボードを更新する

### 要件7: データ移行と後方互換性

**ユーザーストーリー:** 既存のかんばんユーザーとして、現在のタスクが新しい状態システムとシームレスに動作することを望む。これにより、アップグレード中にデータを失わない。

#### 受入れ基準

1. アプリケーションがレガシーデータを読み込むとき、移行システムはデータバージョンを検出する
2. 移行システムは、レガシーのTaskStatus列挙値をカスタム状態オブジェクトに変換する
3. 移行システムは既存のタスクを保持し、移行された状態に割り当てる
4. データ破損が検出された場合、移行システムは不整合を修復し、エラーをログに記録する
5. 移行システムは将来の移行のためにバージョン情報を維持する

### 要件8: 色遷移アニメーション

**ユーザーストーリー:** かんばんユーザーとして、状態色が変更されるときのスムーズな視覚的フィードバックを望む。これにより、状態順序と視覚的外観の関係を理解できる。

#### 受入れ基準

1. 状態順序が変更されるとき、状態列は300ミリ秒間で色遷移をアニメーション化する
2. 状態列はスムーズな色変更のためにCSS遷移を使用する
3. 状態設定モーダルが色プレビューを表示するとき、プレビューは並び替え中にリアルタイムで更新される
4. アニメーションはアクセシビリティ標準を維持し、ユーザーのモーション設定を尊重する
5. ユーザーがモーション軽減設定を有効にしている場合、状態列は遷移の代わりに即座の色変更を使用する

### 要件9: 状態名パーサーとバリデータ

**ユーザーストーリー:** かんばんユーザーとして、確信を持って状態名を入力したい。これにより、技術的エラーなしに意味のあるワークフローステージを作成できる。

#### 受入れ基準

1. ユーザーが状態名を入力するとき、状態バリデータは入力を解析し、空白文字をトリムする
2. 状態バリデータは、空の名前または空白文字のみを含む名前を拒否する
3. 状態バリデータは、同じ設定内での重複する状態名を防止する
4. バリデーションが失敗した場合、状態バリデータは説明的なエラーメッセージを返す
5. 状態フォーマッタは、インターフェース全体での一貫した表示のために有効な名前をフォーマットする

### 要件10: 状態設定シリアライゼーション

**ユーザーストーリー:** システム管理者として、状態設定が確実に保存・取得されることを望む。これにより、ユーザーがカスタマイゼーションを失わない。

#### 受入れ基準

1. 状態シリアライザは保存のために状態設定をJSON形式に変換する
2. 状態デシリアライザは保存されたJSONを解析し、状態オブジェクトを再作成する
3. すべての有効な状態設定について、シリアライゼーションしてからデシリアライゼーションすると等価なオブジェクトが生成される（ラウンドトリップ特性）
4. 状態シリアライザは将来の互換性のためにバージョンメタデータを含める
5. デシリアライゼーションが失敗した場合、状態デシリアライザはデフォルトの状態設定を返し、エラーをログに記録する
